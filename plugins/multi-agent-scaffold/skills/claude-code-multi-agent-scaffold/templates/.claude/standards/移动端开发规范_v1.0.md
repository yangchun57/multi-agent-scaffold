## 第 0 章 总则

### 原则

本规范为 Flutter 移动端 APP 的技术开发提供统一约定，目的有三：统一团队技术决策、传承工程经验、为 AI 编码助手提供代码生成约束。规范领域无关，任何 Flutter APP 可直接采用。规范只约束技术实现，不约束团队流程（分支策略、审核闭环、任务卡等因团队而异，不在本规范范围内）。

### 抽象规则

- 适用范围 `MUST` 限定为 Flutter / Dart 技术栈的移动端 APP；非 Flutter 项目不适用。
- 规范 `MUST` 保持领域无关：规则陈述与代码示例不出现特定业务域名词或项目路径。
- 读者：团队成员（技术决策对齐）、新成员（入项目学习）、AI 编码助手（代码生成约束）。
- 术语：
  - **门面（Facade）**：统一数据访问入口，屏蔽底层实现（Mock/Real、网络客户端）。
  - **设计 Token**：集中定义的颜色/字号/间距/圆角等视觉常量。
  - **三态**：页面加载的 loading / error / data 三种状态。
  - **编译时开关**：通过 `dart-define` 注入的编译期常量，无运行时分支开销。
- 规范分级（RFC 2119 风格）：

| 级别 | 含义 | 违反后果 |
|------|------|----------|
| `MUST` | 强制规则 | 不合格，PR 阻断 |
| `MUST NOT` | 明确反模式 | 不合格，PR 阻断 |
| `SHOULD` | 强烈建议 | 偏离须在 PR 说明理由 |
| `MAY` | 可选优化 | 无强制要求 |

- 本规范为技术约定的权威来源；项目操作参考文档（构建命令、路由表等）`SHOULD` 链接到本规范并保持一致。
- 各章以**通用代码示例**说明模式，示例为通用 Dart 代码，`MUST NOT` 引用特定项目路径或业务域名词。

### ⛔ 反模式

- 规范与操作参考文档内容冲突且未同步
- 规则陈述或代码示例嵌入特定业务域假设或项目路径
- 将团队流程（分支策略、审核闭环）写入技术规范

## 第 1 章 工程结构与分层

### 原则

按职责分层，依赖单向流动，业务域（feature）之间相互解耦。清晰的分层让每个模块有单一职责、明确的依赖方向，便于独立理解、测试与替换。

### 抽象规则

- 顶层目录 `MUST` 划分为：`app/`（路由与主题）、`shell/`（导航容器）、`core/`（基础设施：网络、数据、工具）、`shared/`（跨业务共享组件）、`features/`（按业务域组织页面）。
- 依赖方向 `MUST` 为：`features -> core -> 框架`、`features -> shared`。
- `SHOULD` 避免 `shared -> features`、`core -> features` 的反向依赖。
- 文件命名 `MUST` 用 snake_case，类名 `MUST` 用 PascalCase。
- feature 目录 `SHOULD` 聚焦单一业务域，以页面 Widget 为主，可按需拆 `widgets/` 子目录。

### 代码示例

```
lib/
├── app/                    # 路由与主题
│   ├── routes.dart
│   └── theme.dart
├── shell/                  # 导航容器
│   └── main_shell.dart
├── core/                   # 基础设施
│   ├── network/
│   ├── data/
│   └── widgets/
├── shared/                 # 跨业务共享组件
│   └── widgets/
└── features/               # 按业务域组织
    ├── auth/
    ├── home/
    └── [domain]/
        ├── xxx_page.dart
        └── widgets/
```

### ⛔ 反模式

- 跨 feature 直接依赖（如 `features/a` 直接 import `features/b` 的内部 Widget）--业务域耦合，难独立演进
- core 反向依赖 features --基础设施层耦合业务，无法复用
- 单文件承载多职责（god file）--难维护、难测试

## 第 2 章 导航与路由

### 原则

路由集中注册，路径可读自解释，Tab 页状态可保持。统一的导航结构让页面跳转可预测、可深链，且 Tab 切换不丢状态。

### 抽象规则

- `MUST` 用命名路由：集中定义路由常量 + `routes` Map 注册，`MUST NOT` 硬编码路径字符串。
- 路径 `MUST` 用 kebab-case（`/domain/action` 或 `/domain/action-sub`）。
- Tab 容器 `MUST` 用 `IndexedStack` 保持各 Tab 页面状态；`MUST NOT` 用无保状态的 `PageView` 承载需保持状态的 Tab。
- 独立页面（非 Tab）`MUST` 用 `Navigator.push`，不进 Tab 栈。
- `MUST` 设独立启动页为初始路由（如启动屏/引导页），`MUST NOT` 将初始路由直连业务页。
- 新增路由 `MUST` 三步：加路由常量 -> 注册到 `routes` Map -> 实现 Widget。

### 代码示例

命名路由集中注册：

```dart
class AppRoutes {
  static const String home = '/';
  static const String splash = '/splash';
  static const String itemDetail = '/item/detail';

  static Map<String, WidgetBuilder> get routes => {
        home: (_) => const MainShell(),
        splash: (_) => const SplashPage(),
        itemDetail: (_) => const ItemDetailPage(),
      };
}
```

Tab 容器用 `IndexedStack` 保持状态：

```dart
class MainShell extends StatefulWidget {
  const MainShell({super.key});
  @override
  State<MainShell> createState() => _MainShellState();
}

class _MainShellState extends State<MainShell> {
  int _index = 0;
  final List<Widget> _pages = const [
    HomePage(),
    LibraryPage(),
    ProfilePage(),
  ];

  @override
  Widget build(BuildContext context) {
    return Scaffold(
      body: IndexedStack(index: _index, children: _pages),
      bottomNavigationBar: BottomNavigationBar(
        currentIndex: _index,
        onTap: (i) => setState(() => _index = i),
        items: const [
          BottomNavigationBarItem(icon: Icon(Icons.home), label: '首页'),
          BottomNavigationBarItem(icon: Icon(Icons.library_books), label: '库'),
          BottomNavigationBarItem(icon: Icon(Icons.person), label: '我的'),
        ],
      ),
    );
  }
}
```

### ⛔ 反模式

- 硬编码路径字符串散落各处--改路由需全文搜索
- 深嵌套 push 栈--难返回、难深链
- Tab 用 `PageView` 无保状态--切回 Tab 状态丢失
- 初始路由直连业务页--跳过启动/登录流程

## 第 3 章 状态管理

### 原则

状态分层管理：页面局部状态用轻量手段（`setState`），跨页面/全局共享状态用状态管理框架。避免 prop drilling 和全局单例滥用，让状态作用域与需求匹配。

### 抽象规则

- 页面局部状态（单页内、随页面销毁）`SHOULD` 用 `setState`。
- 跨页面/全局/需持久状态 `MUST` 用状态管理框架（如 Riverpod）。
- `MUST NOT` 用全局单例（静态变量）管理跨页面业务状态。
- `MUST NOT` 用 `setState` 管理需跨页面共享的状态（导致 prop drilling）。

### 代码示例

页面局部状态用 `setState`（三态）：

```dart
class ItemListView extends StatefulWidget {
  const ItemListView({super.key});
  @override
  State<ItemListView> createState() => _ItemListViewState();
}

class _ItemListViewState extends State<ItemListView> {
  List<dynamic> _items = [];
  bool _isLoading = true;
  String? _error;

  @override
  void initState() {
    super.initState();
    _loadItems();
  }

  Future<void> _loadItems() async {
    setState(() { _isLoading = true; _error = null; });
    try {
      final result = await ApiClient().get('/items');
      if (!mounted) return;
      setState(() {
        _items = result['data']['items'] as List<dynamic>;
        _isLoading = false;
      });
    } catch (e) {
      if (!mounted) return;
      setState(() { _error = '加载失败'; _isLoading = false; });
    }
  }
}
```

跨页面共享状态用 Riverpod：

```dart
final userProvider = StateNotifierProvider<UserNotifier, User?>((ref) {
  return UserNotifier();
});
```

### ⛔ 反模式

- prop drilling（状态层层透传）--代码冗余、难追溯
- 全局静态变量当状态容器--无生命周期、难测试、状态来源不明
- `setState` 管跨页面状态--状态随页面销毁丢失、无法共享

## 第 4 章 网络与数据门面

### 原则

业务代码只与统一门面交互，底层数据源（Mock/Real、网络客户端）可替换。门面屏蔽实现细节，使前端可独立于后端开发，且数据源切换无业务代码改动。

### 抽象规则

- `MUST` 经统一门面访问数据，业务代码 `MUST NOT` 直接持有网络客户端。
- 数据源切换 `MUST` 用编译时常量分支，`MUST NOT` 用运行时 `if(mock)` 判断（避免运行时开销与遗漏分支）。
- 门面 `SHOULD` 用单例。
- 新增端点 `MUST` 三处同步：Mock 实现、Real 实现、Mock 数据文件。

### 代码示例

编译时开关（无运行时分支）：

```dart
class ApiConfig {
  static const bool useMock =
      bool.fromEnvironment('USE_MOCK', defaultValue: false);
  static const int mockLatencyMs = 500;
}
```

统一门面（单例 + 编译时分发）：

```dart
class ApiClient {
  static final ApiClient _instance = ApiClient._();
  factory ApiClient() => _instance;
  ApiClient._();

  final MockApiClient _mock = MockApiClient();
  final RealApiClient _real = RealApiClient();

  Future<Map<String, dynamic>> get(String path,
      {Map<String, dynamic>? params}) {
    if (ApiConfig.useMock) return _mock.get(path, params: params);
    return _real.get(path, params: params);
  }

  Future<Map<String, dynamic>> post(String path,
      {Map<String, dynamic>? data}) {
    if (ApiConfig.useMock) return _mock.post(path, data: data);
    return _real.post(path, data: data);
  }
}
```

### ⛔ 反模式

- 页面直接调网络客户端--数据源耦合业务、无法 Mock
- 运行时 `if(mock)` 分支--性能开销、易漏分支
- 端点漏同步（Mock 加了 Real 没加）--Mock/Real 行为不一致，切换时崩溃

## 第 5 章 Mock 与开发演示模式

### 原则

前端可独立于后端开发与演示。Mock 数据须逼真（模拟延迟、错误）且不可变（防污染），使开发期与演示期行为接近真实，且后端就绪后可一键切换。

### 抽象规则

- `MUST` 用编译时 `dart-define` 注入 Mock 开关，无运行时分支。
- Mock 数据 `MUST` 以深不可变缓存返回，防调用方修改污染缓存。
- `SHOULD` 模拟网络延迟与错误场景。
- `MAY` 提供演示账号与演示旅程。
- 后端就绪后 `MUST` 可一键切换真实模式（改 `dart-define` 即可，无业务代码改动）。

### 代码示例

深不可变缓存 + 延迟模拟：

```dart
class MockApiClient {
  static final MockApiClient _instance = MockApiClient._();
  factory MockApiClient() => _instance;
  MockApiClient._();

  final Map<String, Map<String, dynamic>> _cache = {};

  Future<Map<String, dynamic>> loadMockData(String filename) async {
    if (_cache.containsKey(filename)) return _cache[filename]!;
    final json = await rootBundle.loadString('assets/mock_data/$filename');
    final decoded = jsonDecode(json) as Map<String, dynamic>;
    final frozen = _deepUnmodifiable(decoded) as Map<String, dynamic>;
    _cache[filename] = frozen;
    return frozen;
  }

  Future<void> simulateLatency() async =>
      Future.delayed(Duration(milliseconds: ApiConfig.mockLatencyMs));

  // 递归转不可变，防调用方修改污染缓存
  static dynamic _deepUnmodifiable(dynamic source) {
    if (source is Map<String, dynamic>) {
      final result = <String, dynamic>{};
      source.forEach((k, v) => result[k] = _deepUnmodifiable(v));
      return Map<String, dynamic>.unmodifiable(result);
    } else if (source is List) {
      return List.unmodifiable(source.map(_deepUnmodifiable));
    }
    return source;
  }
}
```

### ⛔ 反模式

- 可变缓存被调用方修改--后续读取得到脏数据
- Mock 与 Real 接口签名不一致--切换时崩溃
- Release 包误带 Mock--生产环境返回假数据

## 第 6 章 设计体系与共享组件

### 原则

视觉一致性靠设计 Token 与共享组件库，而非散落硬编码。Token 集中定义、主题映射、组件优先复用，让 UI 统一可维护，改色改距一处生效。

### 抽象规则

- 颜色/字号/间距/圆角 `MUST` 集中定义为设计 Token，`MUST NOT` 在页面内硬编码色值。
- 主题 `MUST` 将 Token 映射到组件库（如 Material3）。
- 新页面 `MUST` 优先复用 `shared/widgets/` 共享组件，`MUST NOT` 重复造同类组件。
- 新页面 `MUST` 用当前活跃设计版本；存量旧版本页面"接触即改"（修改时顺带迁移，不强制批量重构）。

### 代码示例

设计 Token + 主题映射：

```dart
class AppColors {
  static const Color primary = Color(0xFF10B981);
  static const Color primaryDark = Color(0xFF059669);
  static const Color background = Color(0xFFF1F5F3);
  static const Color surface = Color(0xFFFFFFFF);
  static const Color textBody = Color(0xFF334155);
  static const Color textMuted = Color(0xFF64748B);
  static const Color border = Color(0xFFE2E8F0);
  static const Color danger = Color(0xFFEF4444);
}

class AppTheme {
  static ThemeData get lightTheme => ThemeData(
        useMaterial3: true,
        colorScheme: const ColorScheme.light(
          primary: AppColors.primary,
          surface: AppColors.surface,
          onSurface: AppColors.textBody,
          error: AppColors.danger,
        ),
        scaffoldBackgroundColor: AppColors.background,
      );

```

共享页面骨架组件（置于 `shared/widgets/`）：

```dart
class AppScaffold extends StatelessWidget {
  const AppScaffold({super.key, this.title, required this.child, this.scrollable = false});
  final String? title;
  final Widget child;
  final bool scrollable;

  @override
  Widget build(BuildContext context) {
    final content = Padding(
      padding: const EdgeInsets.all(16),
      child: child,

      backgroundColor: AppColors.background,
      body: SafeArea(
        child: scrollable ? SingleChildScrollView(child: content) : content,
      ),
    );
  }

```

### ⛔ 反模式

- 硬编码色值/间距--改主题需全文搜索
- 页面内重复造同类组件--风格不一致、维护倍增
- 新页面用旧版 Token--视觉割裂、迁移债累积

## 第 7 章 页面编码范式

### 原则

页面结构一致，状态显式可观测。统一的页面范式让每个页面可预测：三态字段显式声明、异步安全、骨架统一，降低理解与维护成本。

### 抽象规则

- 需加载远程数据或维护交互状态的页面 `MUST` 为 `StatefulWidget`，结构：字段声明 -> `initState` 触发加载 -> 异步加载方法 -> `build`；纯静态展示页 `MAY` 用 `StatelessWidget`。
- `MUST` 维护三态字段：`_isLoading` / `_error` / data。
- 异步操作后 `MUST` 检查 `mounted` 再 `setState`，`MUST NOT` 在未检查 `mounted` 时 `setState`。
- `MUST` 用统一页面骨架（如 `AppScaffold`）+ 状态视图（如 `StateView`）渲染三态。

### 代码示例

```dart
class ItemListView extends StatefulWidget {
  const ItemListView({super.key});
  @override
  State<ItemListView> createState() => _ItemListViewState();
}

class _ItemListViewState extends State<ItemListView> {
  List<dynamic> _items = [];
  bool _isLoading = true;
  String? _error;

  @override
  void initState() {
    super.initState();
    _loadItems();                              // initState 触发加载
  }

  Future<void> _loadItems() async {
    setState(() { _isLoading = true; _error = null; });
    try {
      final result = await ApiClient().get('/items');
      if (!mounted) return;                    // 异步后检查 mounted
      setState(() {
        _items = result['data']['items'] as List<dynamic>;
        _isLoading = false;
      });
    } catch (e) {
      if (!mounted) return;
      setState(() { _error = '加载失败'; _isLoading = false; });
    }
  }

  @override
  Widget build(BuildContext context) {
    return AppScaffold(
      title: '列表',
      scrollable: true,
      child: _buildBody(),                     // 三态分支
    );
  }

  Widget _buildBody() {
    if (_isLoading) return const StateView.loading(message: '加载中...');
    if (_error != null) return StateView.error(
      title: _error!, message: '请重试',
      action: TextButton(onPressed: _loadItems, child: const Text('重试')),
    );
    return Column(children: _items.map(_buildItem).toList());
  }
}
```

### ⛔ 反模式

- 异步后不检查 `mounted` 直接 `setState`--页面已销毁时抛异常
- 状态字段随意命名/缺失--状态不可观测、难调试
- 跳过状态视图直接渲染数据--无加载/错误态、体验残缺

## 第 8 章 错误处理与状态视图

### 原则

错误显式分层，用户可见可重试。区分错误类型、统一三态渲染、提供重试入口，让错误不静默、用户不无助、技术细节不外泄。

### 抽象规则

- `MUST` 区分网络错误 / 业务错误码 / 未知异常。
- `MUST` 用统一状态视图渲染 loading / empty / error 三态，`MUST` 提供重试入口。
- 异常 `MUST` 在门面层抛出、页面层捕获并转入 `_error` 状态。
- 非阻断提示 `SHOULD` 用 SnackBar/Toast；阻断性错误 `MUST` 用状态视图。
- 面向用户的错误信息 `MUST NOT` 暴露技术细节（堆栈、内部码）。

### 代码示例

统一状态视图组件（置于 `shared/widgets/`）：

```dart
class StateView extends StatelessWidget {
  const StateView._({this.icon, this.title, this.message, this.action});
  final IconData? icon;
  final String? title;
  final String? message;
  final Widget? action;

  factory StateView.loading({String? message}) =>
      const StateView._(icon: Icons.hourglass_top, title: '加载中');
  factory StateView.error({required String title, String? message, Widget? action}) =>
      StateView._(icon: Icons.error_outline, title: title, message: message, action: action);
  factory StateView.empty({required String title, String? message}) =>
      StateView._(icon: Icons.inbox_outlined, title: title, message: message);

  @override
  Widget build(BuildContext context) {
    return Center(child: Column(
      mainAxisSize: MainAxisSize.min,
      children: [
        if (icon != null) Icon(icon, size: 48, color: AppColors.textMuted),
        if (title != null) ...[
          const SizedBox(height: 12),
          Text(title!, style: Theme.of(context).textTheme.titleMedium),
        ],
        if (message != null) ...[
          const SizedBox(height: 4),
          Text(message!, style: const TextStyle(color: AppColors.textMuted)),
        ],
        if (action != null) ...[const SizedBox(height: 16), action!],
      ],
    ));
  }
}
```

页面三态分支 + 重试入口见第 7 章 `_buildBody`。

### ⛔ 反模式

- 静默吞错（catch 后空处理）--问题被掩盖、难排查
- 只 `print` 不提示用户--用户无感知、体验差
- 无重试入口--一次失败永久卡死
- 技术堆栈/内部码直达用户--不专业、泄露实现

## 第 9 章 测试与质量门禁

### 原则

测试分层，质量可门禁化。单元测试覆盖纯逻辑、集成测试覆盖旅程，静态分析必过。让质量可自动校验、不依赖人工把关。

### 抽象规则

- 单元测试 `MUST` 覆盖纯逻辑/数据层，不依赖 Flutter binding。
- 集成测试 `MUST` 在 Mock 模式下运行（`--dart-define=USE_MOCK=true`），`MUST NOT` 依赖外部网络。
- `MUST` 过静态分析（如 `flutter analyze`）且无警告。
- 测试文件 `MUST` 命名 `*_test.dart`，用描述式用例名。

### 代码示例

单元测试（纯逻辑，无 binding）：

```dart
// test/core/network/mock_api_client_test.dart
import 'package:flutter_test/flutter_test.dart';

void main() {
  group('MockApiClient', () {
    test('loadMockData 返回深不可变数据，修改抛异常', () async {
      final client = MockApiClient();
      final result = await client.loadMockData('items_mock.json');

      expect(() => result['data'] = 'tampered', throwsUnsupportedError);
    });
  });
}
```

集成测试（须带 `USE_MOCK`）：

```dart
// test/integration/journey_test.dart
// 运行：flutter test --dart-define=USE_MOCK=true test/integration/journey_test.dart
import 'package:flutter_test/flutter_test.dart';

void main() {
  testWidgets('登录 -> 列表 -> 详情 旅程', (tester) async {
    // 旅程级集成测试，依赖 Mock 数据
  });
}
```

质量门禁命令：

```bash
flutter analyze                                  # MUST 无警告
flutter test --dart-define=USE_MOCK=true         # 全量测试
```

### ⛔ 反模式

- 集成测试不带 `USE_MOCK`--连真实后端、不稳定
- 静态分析警告被忽略--代码质量滑坡
- 测试连真实后端--环境依赖、CI 不稳定

## 第 10 章 构建、发布与资源管理

### 原则

构建可切换、资源受控、双端一致。编译时开关切换模式、构建脚本统一产物、资源与版本受控、双端差异文档化，让发布可重复、仓库不膨胀。

### 抽象规则

- 编译时开关 `MUST` 用 `dart-define`（如 `USE_MOCK`）。
- Release 产物 `MUST` 有统一构建脚本与固定输出目录。
- iOS/Android 双端差异（签名、平台原生配置）`MUST` 文档化。
- 版本号 `MUST` 语义化（`pubspec.yaml` 的 `version`）。
- 资源 `MUST` 在 `pubspec.yaml` 的 `assets` 注册。
- 单文件 `MUST` 小于代码托管平台硬限（如 100MB）；超限 `MUST` 用 LFS 或不入库。
- 二进制模型/大资源 `SHOULD` gitignore，手动放置并文档化。

### 代码示例

`pubspec.yaml` 资源注册 + 语义化版本：

```yaml
name: my_app
version: 1.0.0+1    # 语义化：name.version+buildNumber

environment:
  sdk: ^3.12.2

flutter:
  uses-material-design: true
  assets:
    - assets/mock_data/
    - assets/images/
    - assets/models/      # 二进制模型 gitignore，目录仍注册
```

构建脚本（带编译时开关）：

```bash
# Mock 演示模式
flutter build apk --release --dart-define=USE_MOCK=true
# 真实 API 模式
flutter build apk --release
# iOS
flutter build ipa --release --dart-define=USE_MOCK=true
```

`.gitignore` 策略（二进制模型不入库）：

```
assets/models/*.onnx
```

### ⛔ 反模式

- 大文件直入库--仓库膨胀、克隆失败
- assets 未注册--运行时资源缺失崩溃
- 版本号随意--发布追溯困难
- 二进制模型入库--仓库膨胀、更新困难

## 第 11 章 附录

### 新增功能标准步骤 checklist

1. 在 `lib/features/[domain]/` 创建页面 Widget（StatefulWidget + setState 标准结构）
2. 在 `lib/app/routes.dart` 加路由常量 + 注册到 `routes` Map
3. 如需 API：在 `MockApiClient` 与 `RealApiClient` 各加路由分支 + 在 `assets/mock_data/` 加 Mock JSON（三处同步）
4. 在 `pubspec.yaml` 的 `assets` 注册新资源文件
5. 页面用 `AppScaffold` 骨架 + `StateView` 三态 + `shared/widgets/` 共享组件
6. 写测试：单元测试（纯逻辑）+ 集成测试（带 `--dart-define=USE_MOCK=true`）
7. 过 `flutter analyze` 无警告

|------|------|------|
| 文件 | snake_case | `user_profile_page.dart` |

| 测试文件 | `*_test.dart` | `auth_service_test.dart` |

### 反模式索引

汇总 Ch1–Ch10 各 ⛔ 条目，按章号检索：
