# 移动端开发规范_v1.0 · 第 1 章 工程结构与分层

> 拆分自《移动端开发规范_v1.0》第 2 节。需要全量上下文时读原文件。


### 原则

按职责分层，依赖单向流动，业务域（feature）之间相互解耦。清晰的分层让每个模块有单一职责、明确的依赖方向，便于独立理解、测试与替换。

### 抽象规则

- 顶层目录 `MUST` 划分为：`app/`（路由与主题）、`shell/`（导航容器）、`core/`（基础设施：网络、数据、工具）、`shared/`（跨业务共享组件）、`features/`（按业务域组织页面）。
- 依赖方向 `MUST` 为：`features -> core -> 框架`、`features -> shared`。
- `SHOULD` 避免 `shared -> features`、`core -> features` 的反向依赖。
- 文件命名 `MUST` 用 snake_case，类名 `MUST` 用 PascalCase。
- feature 目录 `SHOULD` 聚焦单一业务域，以页面 Widget 为主，可按需拆 `widgets/` 子目录。

### 代码示例

```
lib/
├── app/                    # 路由与主题
│   ├── routes.dart
│   └── theme.dart
├── shell/                  # 导航容器
│   └── main_shell.dart
├── core/                   # 基础设施
│   ├── network/
│   ├── data/
│   └── widgets/
├── shared/                 # 跨业务共享组件
│   └── widgets/
└── features/               # 按业务域组织
    ├── auth/
    ├── home/
    └── [domain]/
        ├── xxx_page.dart
        └── widgets/
```

### ⛔ 反模式

- 跨 feature 直接依赖（如 `features/a` 直接 import `features/b` 的内部 Widget）--业务域耦合，难独立演进
- core 反向依赖 features --基础设施层耦合业务，无法复用
- 单文件承载多职责（god file）--难维护、难测试
