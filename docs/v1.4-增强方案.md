## 〇、结论先行

我们与OmO 是**范式同级、引擎不同**。编排层、规范层、流水线层我们都已具备，且业务贴合度更高（21 Agent 对 .NET 8 + Vue 3 多租户 vs 它的 11 个通用编程 Agent）。

文章里 5 个可借鉴点，经核实后**只有 2 个是真缺口，2 个是锦上添花，1 个我们学不来**。因此本方案不铺开 5 条线，只做 3 件事：

| 优先级 | 动作 | 解决什么 | 改动量 |
|---|---|---|---|
| **P0** | 新增方案元评审门禁（2 Agent + 1 道闸） | 补上"方案没人挑刺"的真缺口 | 3 个新文件 + 1 命令改|
| **P1** | 模型分级降本（16 opus → 分层） | 降低成本，同时用流程补能力 | 16 处 frontmatter |
| **P2** | 生成器上下文瘦身 | 降低每次会话 token 消耗 | 模板 2 文件 + 脚本 1 处 |

**明确不做**：引入 OmO 源码（SUL 许可限制：仅限内部非商业使用，不可免费分发）、照搬 11 Agent 体系、模型动态路由（引擎层能力，我们学不来）。

## 一、必须先说清的事实与限制

### 1.1 一处改动，两处同步

```
plugins/multi-agent-scaffold/agents/        ← 插件本体（已安装项目用）
plugins/.../skills/.../templates/.claude/agents/   ← 生成器模板（新项目用）
```

**任何 Agent / 命令的新增与修改，都必须两处同步**，否则"插件安装的团队"和"脚手架生成的团队"会出现能力分叉。这是所有方案项的隐含成本，评审时请一并计入。

### 1.2 我们学不来的三件事（诚实边界）

| OmO 能力 | 为什么学不来 |
|---|---|
| **模型按任务动态路由**（quick/deep/visual/ultrabrain 自动选模型） | 这是 OpenCode **引擎层**能力。Claude Code 的 subagent `model` 是 frontmatter **静态字段**，运行时不可变。我们只能做"按角色性质静态分级"，不是"按任务动态路由"。文章把这块讲得最神，但这是它引擎的功劳，不是方法论的功劳。 |
| **Team Mode 8 路并行** | 同样属引擎调度能力。Claude Code 可并行发起多个 Task，但缺乏 OmO 那样的 tmux 可视化与统一上下文管理。**我们现有编排是刻意的串行设计**——`req-coordinator` 写明"串行执行"是为了让评审结论可追溯、避免并发写冲突。不建议为此改架构。 |
| **Hashline 哈希锚定编辑** | 依赖引擎层"每行绑内容哈希、改前校验"。Hook 层只能做近似（git diff 兜底），价值大幅衰减。**降级为不做。** |

## 二、P0：方案元评审门禁（核心补充）

### 2.1 要补的缺口

当前 `/new-feature` 流程里：

```
第一步  pm 产出 task-plan.md
第二步  主 Agent 展示给用户，等拍板      ← 门禁在人身上
第三步  architect 产出架构与接口契约
        ↓直接进 db-engineer             ← architect 的方案没人挑刺
第四步  backend-dev / frontend-dev 开始写代码
```

两个问题：
1. 方案**可验证性**靠人眼扫，人会疲劳、会拍脑袋；
2. `architect` 是**执行者不是评审者**——它自己产出的方案没人挑刺。现有 6 个 `req-*` reviewer 审的是「需求文档质量」和「实现合规性」，**不审架构方案本身**。

### 2.2 借鉴 OmO 的规划三链

OmO 的 `Prometheus → Metis → Momus` 是全部设计里最值得抄的一条：

| OmO Agent | 方法论内核 | 我们对应 |
|---|---|---|
| Prometheus | 编码前访谈澄清模糊需求 | 已有 `requirement-analyst` ✅ |
| **Metis** |专挑"AI 容易翻车的边界场景" | **缺失** → 新增 `plan-risk-analyst` |
| **Momus** | 三重标准校验：**清晰度 / 完整性 / 可验证性** | **缺失** → 新增 `plan-gatekeeper` |

### 2.3 落地设计

**新增 Agent 1：`plan-risk-analyst`**（只读）
- 职责：对已产出的架构方案 + 接口契约 + 数据库设计做**失效点扫描**
- 只读权限（`Read, Glob, Grep, Bash`），不改代码
- 强制检查清单（我们业务特化，非通用泛化）：
  - 并发/事务边界缺失（多租户隔离是否在DB 层兜住）
  - 字段映射断裂（后端 PascalCase ↔ 前端 camelCase，`pageIndex/pageSize`、`items/total`）
  - 分层越界（Controller 直调 SqlSugar、跨层直调）
  - 契约缺口（api-contracts 有接口但database-design 无对应表，反之亦然）
  - 软删除/唯一索引/租户字段缺失（多租户系统高频坑）
- 输出：风险清单，每项含 `严重度 / 位置 / 触发条件 / 建议`

**新增 Agent 2：`plan-gatekeeper`**（只读）
- 职责：对 `plan-risk-analyst` 的输出 + 方案本身做**放行判定**
- 三重校验，各出独立结论（对应 Momus 三标准）：
  1. **清晰度**：另一人（无上下文）能否只看文档就理解要做什么
  2. **完整性**：需求 → 契约 → 表 → 代码路径 是否无断点
  3. **可验证性**：是否有可测的验收判据（不是"接口能通"，是"边界/异常有断言"）
- 输出：`PASS` / `CONDITIONAL PASS`（列条件）/ `REJECT`（列阻塞项）
- **硬约束**：`REJECT` 时主Agent 不得进入编码阶段

**新增命令**：`/plan-gate`（独立可复用，便于存量项目补做）
```
/plan-gate  → plan-risk-analyst 扫描 → plan-gatekeeper 判定 → 门禁结论
```

**串联位置**：插在 `new-feature` 第三步architect 完成之后、db-engineer 之前：
```
第三步  architect 完成 → `docs: 架构与接口契约`
  ↓ ★新增
      plan-risk-analyst → plan-gatekeeper → 门禁
      REJECT → 回到 architect 修订（不进入编码）
  ↓
     db-engineer → backend-dev → frontend-dev ...
```

### 2.4 为什么这是 P0

它是**唯一一条补真缺口**的改动。规划三链是OmO 全部设计中方法论密度最高的部分，且天然契合我们已有的多租户红线（`tenant_guard.py` 的检查项可以直接复用为 `plan-risk-analyst` 的扫描规则，不用另起炉灶）。

## 三、P1：模型分级降本

### 3.1 现状

21 个 Agent 中 **16 个硬编码 `model: opus`**，5 个 sonnet。这不是设计，是历史默认值。

### 3.2 分级原则

| 层级 | 判据 | Agent |
|---|---|---|
| **opus 保留** | 需要跨文件推理、有歧义禁止、错一次代价高 | `architect`、`bug-fixer`、`pm`、`requirement-analyst`、`functional-tester`、`reviewer`、6 个 `req-*`、2 个 group-lead、`product-designer`、`ux-researcher` |
| **sonnet 下放** | 规范明确、判定可机械核对、确定性执行 | 新增的 `plan-gatekeeper`（三重校验判据固定，最适合下放） |

`plan-risk-analyst` 保持 opus（要推演失效路径，需要深度推理）。

**净变化：新增 1 个 opus、1 个 sonnet，存量16 opus 不动。**

### 3.3 用流程补能力（关键）

Sonnet 下放的前提是**用流程约束换模型能力**。`plan-gatekeeper` 必须：
- 强制按固定顺序过三道校验，**不许跳步、不许合并判断**
- 每条结论必须引文档具体位置（对标 OmO 的"证据驱动"原则）
- 输出机器可判定的结构（PASS/REJECT + 阻塞项列表），不给自由文本

**这是全文最重要的一条工程原则**：模型降级只有在判据足够机械时才安全。

## 四、P2：生成器上下文瘦身

### 4.1 我们其实已经领先了

OmO 的 `/init-deep` 生成三级AGENTS.md。而我们的 `split-standards.py` 已经把规范**按二级标题拆成topics/ 碎片 + INDEX.md**（7 个规范主题目录），粒度比 OmO 更细。

**所以这条不是"补能力"，是"补最后一公里"**——根 `CLAUDE.md` 目前仍可能过长，缺一层"先读索引再按需读碎片"的引导。

### 4.2 改动

1. **模板根 `CLAUDE.md`**：瘦身为「最高优先级红线 + 规范索引表+ 常用命令」，详细内容全部指向 `standards/topics/INDEX.md`
2. **新增目录级 `CLAUDE.md`**：`src/backend/api/`（分层边界）、`src/web/src/`（前端约定）——只写该目录特有的硬约束
3. **`scaffold.py`**：生成后自动跑一次索引校验，确保每个规范文件都在 INDEX 里有条目

## 五、不做与后续

### 明确不做（已评估，无价值或不可行）
- ❌ 引入 OmO/其源码（SUL 许可：仅内部非商业，不可分发）
- ❌ 照搬 11 Agent 体系（业务贴合度低于现有 21 个）
- ❌ Hashline 哈希锚定（引擎层能力，hook 层近似无价值）
- ❌ Team Mode 式并行（我们是刻意的串行设计，改则结论不可追溯）
- ❌ 阶段感知推荐器`/findme`（9 个命令已有明确阶段，收益边际）

### 待评审决策点
1. **P0 是否要做**——新增 2 个 Agent 会让总数21 → 23，README/marketplace/plugin.json 三处描述需同步更新。是否接受这个膨胀？
2. **P0 门禁的强制程度**——`REJECT` 时是**硬阻断**（必须回architect）还是**软提示**（主 Agent 自行判断）？
3. **P2 是否要等P0 落地后再做**——P0 会改动new-feature 流程，若同期改模板易冲突。

### 建议落地顺序
P0（补真缺口）→ P1（降本）→ P2（省token），分三个小版本，v1.4.0 / v1.4.1 / v1.4.2。
